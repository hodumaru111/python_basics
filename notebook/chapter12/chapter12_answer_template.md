# 2. 온라인 강의 데이터의 시스템 역할 분류

다음 데이터를 분류합니다.

| 데이터 | 시스템 역할 | Source of Truth 여부 | 잃어버리면 재구축 가능? | 이유 |
| --- | --- | --- | --- | --- |
| 수강신청 | Source of Truth | 예 | 불가 | 학생이 실제로 신청한 사실 자체라서 다른 데이터로 다시 만들 수 없다 |
| 신청 당시 금액 | Source of Truth | 예 | 불가 | 신청 시점에 기록한 값이라 나중에 강의 가격이 바뀌면 복원할 수 없다 (결제 승인액·매출과는 다름) |
| 로그인 세션 | Ephemeral State | 아니오 | 가능 | 잃어도 인증 원본으로 다시 로그인해 새로 발급하면 된다 |
| 인기 강의 TOP 3 | Derived Cache | 아니오 | 가능 | 수강신청 원본을 집계해서 언제든 다시 계산할 수 있다 |
| 강의 태그/옵션 | Flexible Metadata | 아니오 (핵심 원본은 course_project) | 가능 | 제목·난이도는 원본과 대조해 문서를 다시 만들 수 있다 |
| 학습 행동 이벤트 | Event Log | 예 (이벤트 로그 자체가 원본) | 불가 | 한 번 일어난 행동 기록은 다시 만들 수 없다. 파티션 같은 파생 구조만 재생성 가능 |
| 추천 관계 | Relationship Index | 아니오 | 가능 | 원본 데이터에서 관계 인덱스를 다시 생성할 수 있다 |

사용 가능한 역할 예:

```text
Source of Truth
Derived Cache
Ephemeral State
Flexible Metadata
Event Log
Relationship Index
```

### Source of Truth와 파생 저장소를 구분해야 하는 이유

```text
원본과 파생을 구분하지 않으면 두 값이 서로 다를 때 어느 쪽을 믿어야
할지 알 수 없다. 원본은 잃으면 복구할 수 없으니 백업·트랜잭션으로
엄격히 지켜야 하고, 파생(캐시 등)은 잃어도 원본에서 다시 만들 수 있으니
성능을 위해 느슨하게 다뤄도 된다. 구분해 두면 장애가 났을 때
"원본 기준으로 파생을 재구축한다"는 복구 방향이 분명해진다.
```

## 5-1. 일반 컬럼과 JSONB 영역 구분

| 항목 | 일반 컬럼 / JSONB | 그렇게 둔 이유 |
| --- | --- | --- |
| `source_course_id` | 일반 컬럼 | 원본 강의(`course_project.courses`)와 대조하는 기준 키라서 UNIQUE·NOT NULL 같은 제약을 걸어야 한다 |
| `course_code` | 일반 컬럼 | 문서를 식별하는 값으로 매번 조회하고 중복되면 안 되어서 UNIQUE 제약이 필요하다 |
| `title` | 일반 컬럼 | 모든 문서에 있고 원본 제목과 일치하는지 반복해서 검증하는 안정된 핵심 값이다 |
| `level` | 일반 컬럼 | 모든 문서에 있고 값 범위(basic/intermediate/advanced)를 CHECK로 DB가 지켜줘야 한다 |
| `document_version` | 일반 컬럼 | 낙관적 잠금에서 `WHERE` 조건으로 쓰고 1 이상이어야 하는 규칙을 DB가 강제해야 한다 |
| `tags` | JSONB | 강의마다 개수와 내용이 달라지는 가변 부가 정보라 컬럼을 미리 고정하기 어렵다 |
| `options` | JSONB | `online`, `certificate`처럼 옵션 종류가 늘거나 바뀔 수 있어 문서 안에 유연하게 둔다 |
| `instructor_snapshot` | JSONB | 화면 표시용으로 복사해 둔 강사 정보라서, 구조가 바뀌어도 테이블을 고치지 않고 담을 수 있다 |

### `level`을 JSONB 안에 넣지 않고 일반 컬럼으로 둔 이유

```text
level은 모든 문서에 반드시 있고, 자주 검색하며, 원본과 일치하는지 반복
검증하는 값이다. 일반 컬럼으로 두면 CHECK 제약으로 허용 값(basic,
intermediate, advanced)을 DB가 직접 지켜 주고 NOT NULL도 걸 수 있다.
JSONB 안에 넣으면 이런 제약이 약해지고 검증을 애플리케이션이 맡아야
한다. 그래서 구조와 규칙이 안정적인 값은 일반 컬럼에 둔다.
```

### `instructor_snapshot`이 Source of Truth가 아닌 이유

```text
문서 안의 강사 정보는 course_project.instructors에서 복사해 온 값이다.
화면에 빠르게 보여 주기 위한 파생 복사본일 뿐이라, 원본의 강사 이름이나
전문 분야가 바뀌면 스냅샷은 옛 값으로 남을 수 있다. 둘이 다르면 항상
원본(course_project.instructors)을 신뢰하고, 스냅샷은 원본과 대조해
다시 만들어야 한다.
```

## 5-2. JSONB 조회 결과

```text
사용한 JSONB 조건: metadata @> '{"tags": ["PostgreSQL"]}'::jsonb
                  (tags 배열에 "PostgreSQL"이 포함된 문서)
```

## 5-3. 낙관적 잠금 관찰

```text
읽은 document_version:1
UPDATE 조건에 사용한 version:1
예상 영향 행 수:1
실제 영향 행 수:1
```

### 영향 행 수가 0이면 무엇을 의심해야 하나요?

```text
UPDATE의 WHERE 조건(course_code = 'COURSE-301', document_version = 1,
options가 객체)에 맞는 행이 없다는 뜻이다. 먼저 다른 사용자나 작업이
그 사이에 문서를 수정해서 document_version이 이미 올라갔는지 의심한다.
내가 읽은 version이 오래된 값이거나, course_code·options 경로가 현재
문서와 다른 경우도 확인한다. 0행이면 덮어쓰지 않고 문서를 다시 읽은 뒤
재시도하거나 충돌로 처리한다.
```

### 실습에서 ROLLBACK 후 기준 상태를 유지하는 이유

```text
UPDATE로 COURSE-301의 certificate와 document_version이 바뀐 채 남으면
이후 단계의 기준값(certificate=true, version=1)이 달라진다. 그러면
최종 자동 검증(07)이 실패하고, 다른 사람이 같은 실습을 재현할 수도
없다. ROLLBACK으로 변경을 취소하면 동작은 관찰하면서 기준 데이터는
그대로 유지할 수 있다.
```

## 6-1. Seed 기준

```text
전체 캐시 = 4
Seed 시점 유효 = 3
Seed 시점 만료 = 1
```

| 항목 | 기대 | 실제 |
| --- | ---: | ---: |
| 전체 | 4 | (2번 결과의 total_cache_rows) |
| Seed 시점 유효 | 3 | (valid_at_seed_rows) |
| Seed 시점 만료 | 1 | (expired_at_seed_rows) |

## 6-2. Seed 기준과 현재 시각 기준 차이

```text
현재 유효 캐시 수: (3번 결과의 currently_valid_rows — 본인이 실행한 시점의 값)
```

### 현재 유효 건수를 고정 정답으로 사용하면 안 되는 이유

```text
현재 시각 기준 유효 여부는 CURRENT_TIMESTAMP와 비교하기 때문에 언제
실행하느냐에 따라 결과가 달라진다. 30분짜리 세션은 30분 뒤에는 만료로
바뀐다. 그래서 재현 가능한 기준은 created_at과 비교하는 Seed 시점
판단(4/3/1)이고, 현재 유효 건수는 실행 시각을 함께 적는 참고값으로만
쓴다.
```

## 6-3. 정확 키 조회

```text
조회한 키: course:popular:v2:top3  (7번 쿼리)
결과: cache_value가 비어 있고 cache_status = cache_miss
캐시 미스 여부: 예 (시드에는 v1만 있고 v2 키는 없음)
```

### Key-Value 제품의 TTL과 eviction을 같은 개념으로 보면 안 되는 이유

```text
TTL(만료)은 정해 둔 시간이 지나면 값이 만료되는 것이고, eviction은
메모리가 부족할 때 정책(예: 오래 안 쓴 것부터)에 따라 값을 제거하는
것이다. 만료 시간이 남아 있어도 메모리 압박으로 제거될 수 있으니, 둘을
같은 동작으로 가정하면 "TTL이 남았는데 왜 캐시가 없지?" 같은 상황을
설명하지 못한다. 그래서 캐시는 항상 없을 수 있다는 전제로 원본에서
다시 만들 수 있게 설계해야 한다.
```

### 이 PostgreSQL 테이블이 실제 Redis 같은 Key-Value DB가 아닌 이유

```text
이 테이블은 키로 값을 찾는 개념만 흉내 낸 시뮬레이션이다. 메모리
저장이 아니라 디스크 기반이고, expired_at이 지나도 행이 자동으로
삭제되지 않으며(삭제는 사람이 직접 DELETE 해야 함), eviction·복제·
샤딩·실제 네트워크 성능과 장애 동작도 제공하지 않는다. 그래서 이
실습으로 Redis의 속도나 운영 특성을 판단할 수 없다.
```

# 7. 캐시 장애 사고 실험

상황:

```text
PostgreSQL 원본에서는 인기 강의 순위가 변경되었다.
캐시에는 이전 TOP 3가 남아 있다.
```

다음에 답합니다.

```text
신뢰해야 할 원본: PostgreSQL의 course_project (수강신청·강의 원본 데이터). 캐시는 원본에서 만든 파생 데이터라서 둘이 다르면 원본을 믿는다.

사용자에게 오래된 값을 허용할 수 있는 시간: 약 1시간 이내. (시드의 캐시도 1시간 TTL. 인기 순위는 몇 분 늦어도 서비스에 큰 문제가 없지만, 수강신청 가능 여부 같은 값에는 허용하지 않는다.)

캐시 갱신 방식: 원본 순위가 바뀌면 캐시를 갱신하거나 삭제한다.정해진 시각의 배치 갱신 + 원본 변경 이벤트 시 갱신을 함께 쓴다. 키에 버전(v1, v2)을 넣어 새 버전으로 교체한다.

캐시 삭제 후 재생성 방법: 캐시 미스가 나면 PostgreSQL 원본에서 수강신청을 집계해 TOP 3를 다시 계산하고, TTL과 버전을 붙여 캐시에 저장한다.

캐시 서버 장애 시 fallback: 캐시를 못 읽으면 원본 PostgreSQL을 직접 조회해서 응답한다. 느려질 수는 있어도 핵심 기능은 멈추지 않아야 한다.

동시 재생성 요청이 몰릴 때의 위험: 캐시가 비는 순간 많은 요청이 동시에 집계를 실행해 원본 DB에 부하가 몰린다. 한 요청만 재생성하게 잠금을 걸거나 요청을 합치고, 만료 시각을 조금씩 어긋나게 둔다.
```

### 캐시가 Source of Truth가 되어서는 안 되는 이유

```text
캐시는 속도를 위해 원본에서 복사·계산해 둔 값이라, 만료되거나 메모리
정책에 따라 사라질 수 있고 원본과 어긋날 수도 있다. 캐시를 원본으로
삼으면 값이 사라졌을 때 되살릴 방법이 없고, 오래된 값과 최신 값 중
무엇이 맞는지도 판단할 수 없다. 반대로 원본이 따로 있으면 캐시를 통째로
지워도 원본에서 다시 만들 수 있으니, 캐시는 언제든 버려도 되는 파생
데이터로 설계해야 한다.
```

# 9. 저장 모델 비교표

제품 이름보다 저장 모델을 비교합니다.

| 후보 | 잘 맞는 접근 패턴 | 트랜잭션/일관성 고려 | 재구축 가능성 | 운영·보안·백업 부담 | 현재 판단 |
| --- | --- | --- | --- | --- | --- |
| PostgreSQL RDBMS | 여러 표를 JOIN하고 제약조건으로 무결성을 지켜야 하는 원본 데이터 (수강신청·금액) | 여러 변경을 하나의 트랜잭션으로 묶는 강한 일관성 | 원본이라 잃으면 재구축 불가, 백업·복구가 핵심 | 이미 운영 중이라 추가 부담이 가장 작다 | 채택 (원본) |

| Document | 구조가 자주 바뀌는 문서 단위를 통째로 읽고 쓰는 패턴 | 문서 안에서는 편하지만 여러 문서에 걸친 일관성은 제품별로 확인 필요 | 원본이 따로 있으면 재구축 가능 | 새 서버, 동기화·버전 충돌·보안 관리 필요 | 후보 (JSONB로 먼저 검증) |
| Column-Family | 쓰기가 많고 키·시간 범위로 조회하는 대량 이벤트 로그 | 조회 패턴을 미리 정해야 하고 중복·늦은 도착 처리 정책 필요 | 원본 이벤트 보관본에서 파티션 재생성 | 운영 난이도와 비용이 크고 전문성 필요 | 보류 (규모가 확정될 때까지) |

### “NoSQL은 항상 더 빠르다”가 잘못된 설명인 이유

```text
속도는 저장소 종류가 아니라 어떤 조회를 어떤 데이터 규모와 구조로
하느냐에 달려 있다. 정확한 키 조회에는 Key-Value가 유리할 수 있지만,
여러 표를 JOIN하거나 집계하는 작업은 RDBMS가 더 편하고 빠를 수 있다.
데이터가 3행뿐이면 어느 쪽이든 차이가 없고, 오히려 저장소를 추가해
동기화와 장애 대응 부담만 늘 수 있다. 그래서 "NoSQL이라서 빠르다"가
아니라 "이 조회 패턴에는 이 저장 모델이 맞다"를 PoC로 측정해 판단해야
한다.
```

### 저장소가 하나 추가될 때 새로 생기는 운영 책임 최소 5개

```text
1. 원본과의 동기화 (변경 이벤트·주기적 대조·지연 허용 범위)
2. 재시도와 멱등성 (같은 메시지를 두 번 처리해도 중복이 생기지 않게)
3. 접근 권한과 비밀 관리 (계정·키·네트워크 접근 통제)
4. 백업과 복원 (장애 시 어느 쪽을 어떻게 복구할지)
5. 모니터링과 장애 대응, 버전 업그레이드와 비용
```

### 데이터가 3행뿐이라 인덱스가 있어도 Seq Scan이 합리적일 수 있는 이유

```text
3행짜리 테이블은 전체를 읽는 비용이 거의 없고 한 페이지에 다 들어간다.
인덱스를 거쳐 가면 오히려 인덱스를 읽는 비용이 추가된다. 그래서
플래너가 순차 스캔(Seq Scan)을 더 싸다고 판단할 수 있다. 인덱스가 존재한다는
것과 쓰인다는 것은 다르다. 인덱스 효과는 데이터가 충분히 많고 조건이
일부 행만 골라내는 선택도가 있을 때 나타나고, 쓰기 비용과 저장 공간도
함께 따져야 한다. 이 실습은 성능 증명이 아니라 구조와 대상 질의를
확인하는 것이다.
```

# 13. 개인 프로젝트 저장 전략 결정

## 13-1. Source of Truth

```text
내 프로젝트의 Source of Truth:
PostgreSQL의 order_erd_practice 스키마 (customers, menus, orders, order_details)

그 이유:
주문·주문상세·판매 당시 단가는 한 번 기록되면 다른 데이터에서 다시 만들 수
없는 사실이고, 돈과 수량이 맞아야 하는 데이터다. 주문과 상세, 합계가 함께
맞아야 해서 트랜잭션·FK·CHECK 제약이 필요하고, 이미 PostgreSQL에서
제약조건과 트리거로 지키고 있다.
```

## 13-2. PostgreSQL만 유지할지, 다른 저장 모델을 검토할지

```text
현재 결정: PostgreSQL만 사용
(JSONB·Key-Value·Document·Column-Family·Graph는 추가하지 않는다)
```

### 결정 근거

```text
주요 조회 패턴:
고객별 최근 주문, 주문별 상세 목록, 판매 중인 메뉴 목록, 월별·메뉴별 집계.
모두 표 여러 개를 JOIN하거나 집계하는 조회라서 RDBMS에 잘 맞는다.

일관성 요구:
주문 생성 시 orders, order_details, total_amount가 함께 맞아야 한다.
금액·수량이 틀리면 안 되므로 강한 일관성과 트랜잭션이 필요하다.

파생 데이터 여부:
total_amount·total_quantity는 order_details에서 계산되는 파생 값이다.
인기 메뉴 TOP 10을 만든다면 주문 원본에서 집계하는 파생 데이터가 된다.

재구축 가능 여부:
파생 값은 order_details에서 다시 합산하거나 집계하면 복구할 수 있다.
원본(주문, 판매 당시 단가, 고객)은 잃으면 복구할 수 없어 백업이 핵심이다.

운영 부담:
저장소를 하나 더 두면 동기화, 재시도·멱등성, 모니터링, 접근 권한 관리가
늘어난다. 지금은 PostgreSQL 한 곳만 관리하면 된다.

백업/복구 부담:
PostgreSQL 한 곳만 백업·복원하면 되고, 원본과 파생이 같은 DB 안에 있어
복구 후 불일치가 생길 위험이 작다.

현재 팀 역량:
1인 학습 프로젝트라서 PostgreSQL 운영만 감당할 수 있고, 별도 저장소를
운영·장애 대응할 여력은 없다.
```

> **“현재는 PostgreSQL만 사용한다”도 충분히 좋은 결론입니다.**  
> 기술을 추가하지 않는 이유를 조회 패턴·일관성·운영 책임으로 설명할 수 있어야 합니다.

# 14. 작은 PoC 설계

후보 저장 방식 하나를 골라 실제 도입 전에 확인할 PoC를 설계합니다.

```text
후보 저장 방식: Key-Value (예: Redis 같은 인메모리 Key-Value 저장소)
시스템 역할: Derived Cache (파생 캐시)
Source of Truth 여부: 아니오 (원본은 PostgreSQL의 orders / order_details / menus)

키/문서/파티션/관계 구조:
  키: menu:popular:v1:top10
  값: {"menu_ids": [..10개..], "generated_at": "...", "source": "order_erd_practice"}
  TTL: 1시간, 키에 버전(v1)을 포함

대표 읽기 2개:
  1. 메인 화면에서 menu:popular:v1:top10 키로 인기 메뉴 ID 10개를 읽는다.
  2. 읽은 ID로 menus에서 이름·가격·판매 여부를 조회해 화면에 보여 준다.

대표 쓰기 1개:
  캐시 미스 또는 만료 시 PostgreSQL에서 최근 7일 주문상세를 메뉴별로 집계해
  상위 10개를 계산한 뒤 TTL과 버전을 붙여 캐시에 저장한다.

원본 동기화 방법:
  TTL 만료 시 재생성 + 정해진 주기(예: 10분)의 배치 갱신.
  원본(주문)은 이 캐시를 읽지 않고, 캐시는 원본에서만 값을 가져온다(단방향).

중복/재시도 시 멱등성 처리:
  같은 키에 같은 방식으로 덮어쓰므로 재시도해도 결과가 같다.
  재생성은 키 단위로 한 요청만 수행하도록 잠금을 걸어 중복 계산을 줄인다.

장애 시 fallback:
  캐시를 읽지 못하거나 값이 없으면 PostgreSQL 집계 쿼리를 직접 실행해 응답한다.
  느려질 수는 있어도 주문과 메뉴 조회 같은 핵심 기능은 중단되지 않는다.

재구축 방법:
  캐시 키를 전부 삭제한 뒤 PostgreSQL 주문 집계 쿼리를 다시 실행해 채운다.

보안 요구:
  캐시 값에는 메뉴 ID와 생성 시각만 두고 고객 정보·금액 같은 개인정보는 넣지 않는다.
  접근은 서비스 계정으로 제한하고 접속 정보는 코드에 직접 쓰지 않는다.

백업/복구 방법:
  캐시는 파생 데이터라 별도 백업하지 않는다. 장애나 교체 시 비운 채로 시작하고
  원본에서 재구축한다. 백업 대상은 PostgreSQL 원본이다.
```

## PoC 성공 기준

최소 5개를 작성합니다.

```text
1. 캐시 미스(키 없음) 시 PostgreSQL 원본 집계로 TOP 10이 재생성되고
   캐시에 저장된다.
2. 원본 주문이 바뀐 뒤 정해진 시간(예: 10분) 안에 캐시 값이 새 집계 결과와
   일치하도록 갱신된다.
3. 캐시 서버를 멈춘 상태에서도 인기 메뉴 조회와 주문 처리가 중단되지 않고
   PostgreSQL fallback으로 응답한다.
4. 같은 재생성 요청을 두 번 처리해도 캐시 내용이 같고 중복 데이터나 오류가
   생기지 않는다.
5. 캐시 전체를 삭제해도 원본 PostgreSQL에서 다시 구축할 수 있고, 구축 시간이
   정한 한도(예: 몇 초) 이내이다.
```
